# Test vectors

Test vectors are part of the specification. An implementation conforms only if it passes every vector here.

> **No vectors yet.** They will be generated by `bondpost-core` (milestone M1), then checked by hand or with a second, independent tool before they are committed. Never write expected values by hand.

## Planned files

| File | Covers | Spec |
| --- | --- | --- |
| `derivation.json` | `base_pk`, `nostr_pk`, `L`, `network` → `t`, `K`, `witness_script`, `scriptPubKey`, address | [01](../spec/01-bond-construction.md) |
| `proof-event.json` | Bond and outpoint → unsigned event, event id. Signed events with fixed keys | [02](../spec/02-proof-event.md) |
| `verification.json` | Event plus a mocked chain state → success result, or exactly one failure code | [03](../spec/03-verification.md) |
| `weight.json` | Amount, `L`, `h` → weight, including the cap and the minimum | [04](../spec/04-weight.md) |
| `reclaim.json` | Bond, destination, fee → unsigned transaction and BIP143 sighash | [05](../spec/05-reclaim-and-recovery.md) |

## Required coverage

- At least ten derivation cases, across all three networks.
- `L` values that exercise script-number encoding boundaries: 1, 16, 17, 127, 128, 32767, 32768, 8388607, 8388608 and 499999999.
- A case where `t ≥ n` or `K` is infinity cannot be constructed in practice. Implementations should cover those branches in unit tests instead.
- One verification case for each of the nine failure codes, including a `pubkey` swapped and re-signed, which gives `script_mismatch`.
- Invalid inputs: `L = 0`, `L = 500000000`, an uncompressed `base`, upper-case hex, a leading-zero `vout`, and duplicated tags.

## File format

Each file is a JSON object:

```json
{
  "spec_version": "1",
  "description": "…",
  "cases": [
    { "name": "…", "input": { }, "expected": { } }
  ]
}
```

Each file will be described by a JSON Schema in `schemas/` once its first cases exist. The `bondpost` repository consumes this directory at a pinned spec tag and runs every case in CI.
